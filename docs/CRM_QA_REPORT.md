## Проверенные риски, которые не подтвердились

- Bounded filtered pagination на десяти источниках: 310 исходных публикаций,
  180 подходящих; полный проход в пределах бюджета цепочки без потерь/дубликатов.
  Каждая выдача ≤10 совпадений, ≤50 уникальных просмотренных публикаций, ≤5 страниц.
  Уменьшение сырой страницы до свободных мест не теряет «лишние» совпадения.
- Несколько неподходящих страниц перед совпадением, пустой архив, отсутствие
  сохранённых источников, перекрывающиеся и зацикленные курсоры проверены текущими
  ProjectSearchTest и новым CrmAuditMatrixTest. Пустая ограниченная выдача имеет
  продолжение и не объявляется окончательным отсутствием кандидатов.
- Повтор и конкурентное использование одного continuation возвращают ту же страницу;
  последующее продолжение не повторяет её. Изменение запроса/режима/критериев/источников,
  чужой, повреждённый или потерянный после restart токен отклоняются.
  Отложенный fake ответ после изменения критериев не сохраняет старое evidence.
- AND обязательных слов, OR дополнительных условий MatchingService и NOT исключений
  сохранены. Желательные слова проекта не блокируют результат. Проверены Unicode
  NFKC, полноширинное написание Java, NBSP, фразы и пустой текст. Объяснение означает наличие слов
  в публикации, а не подтверждённую квалификацию человека.
- Родительская coroutine cancellation распространяется; timeout, частичный ответ,
  429/FLOOD_WAIT сохраняют последний завершённый курсор и не запускают бесконечные retries.
- Временные схемы v1, v2, v3, v4, v5, v6, v7 мигрируют в v8 и повторно открываются.
  Сохраняются старые каналы, шаблоны/подписки, прочитанные уведомления, checkpoints;
  импортированные публикации/history cursors начиная с v2, bot recipients с v5,
  saved decisions с v7. Проверены `integrity_check` и `foreign_key_check`.
  Fixtures синтетические, построены из текущей схемы с удалением более новых объектов;
  это не проверка каждого реально существовавшего пользовательского файла базы.
- Искусственная ошибка DDL v8 откатывает весь переход с сохранением `user_version=7`
  и старых таблиц. После устранения причины повторный запуск успешно мигрирует.
- CRUD, изменение требований, удаление связанного шаблона, независимые стадии одной
  публикации в разных проектах, уникальность карточек, rollback записи и состояние
  после повторного открытия SQLite проверены. Архив проекта запрещает изменения и
  приостанавливает собственный мониторинг, сохраняя независимую старую подписку.
- REST 400/404 и cross-project denial покрыты; Host/Origin denial дополнительно
  проверяет отсутствие созданных проектов, а не только HTTP-код.
- Desktop и mobile: создание → источники/требования → поиск → просмотр объяснения →
  добавление → заметка/оценка/классификация → изменение стадии → reload → архив.
  Есть проверка 390 px без горизонтального переполнения. Остальные React-разделы
  проходят общий offline Playwright.

## Производительность на синтетических данных

Локальный macOS Intel, JDK 21, SQLite, один запуск после подготовки данных:

| Данные и операции | Измерение |
| --- | --- |
| 10 000 публикаций архива + 10 000 карточек: шесть страниц по 20 карточек, фильтры/статистика и две страницы поиска | 300 ms суммарно |
| 50 000 публикаций архива + 50 000 карточек: тот же набор | 1318 ms суммарно |
| 50 000 публикаций с двумя шаблонами, 100 000 уведомлений: две страницы уникальных совпадений по 20 | 1206 ms суммарно |

Проверены ограниченный размер ответов, стабильная сортировка при равных значениях,
фильтры и отсутствие повторов между проверенными страницами. Обычная страница карточек
использует COUNT + ограниченный SELECT без поштучных загрузок. Это измерения SQL/service,
не SLA браузера и не доказательство ARM64-производительности. Полный проход всех
50 000 публикаций одной поисковой цепочкой не поддерживается текущим лимитом 10 000.

## Что остаётся непроверенным и ограничения

1. Реальные Telegram-ответы нескольких каналов, server-side offsets на изменяющемся
   канале, настоящий FLOOD_WAIT и доступность оригинальных ссылок. Не выполнялись
   live-поиск, подписка, импорт или отправка; эти проверки требуют единственного
   авторизованного backend и согласованных источников.
2. Прекращение уже отправленного TDLib RPC после отмены coroutine не доказано fake
   портом. Проверена отмена application coroutine и отсутствие продолжения цикла.
3. Search continuations намеренно недолговечны: TTL 10 минут, 128 сохранённых состояний,
   максимум 10 000 просмотренных identities на цепочку. После restart нужен новый поиск;
   проекты/карточки/заметки/стадии и checkpoints мониторинга сохраняются в SQLite.
4. Matching использует существующие excerpts до 4000 символов; слова за их пределами
   и смысл/личность/квалификация человека не устанавливаются. Поиск не является
   неизменяемым snapshot Telegram. Изменения канала между страницами остаются возможны.
5. Бюджет 20 секунд ограничивает чтение источников, а не последующую запись SQLite.
   Offset страницы Kanban могут сдвигаться при конкурентном изменении карточек.
6. Несохранённый draft сохраняется при обновлении видимой карточки, но не обещан при
   уходе из проекта или фильтрации карточки из выдачи. Это не новый draft-storage.
7. Рабочий backend PID 72388 продолжает прежнюю версию `0e833b7`; он не обновлялся
   в рамках аудита. Dev frontend отражает исходники. Для ручной проверки исправлений
   требуется штатный restart единственного backend, без второго TDLib клиента.

## Рекомендация по PR #4

По автоматическим проверкам локального CRM merge можно рекомендовать **при зелёных
GitHub Actions на финальном head**. Подтверждённые дефекты исправлены, пользовательский
сценарий проверен через настоящий REST/SQLite и fake Telegram, новая миграция не нужна.
Это не утверждение о проверке реального Telegram или всех пользовательских баз.
Merge в master в рамках задачи не выполняется.

Для ручной проверки после обновления единственного backend:

1. Открыть «Проекты», создать Senior Java Backend; выбрать сохранённые публичные
   источники, обязательные Java / Spring Boot / PostgreSQL, желательные Kafka / Docker.
2. Поискать в архиве. Проверить найденные слова и объяснение, а при ограниченной пустой
   странице — кнопку продолжения и счётчики. Затем отдельно проверить Telegram.
3. Добавить публикацию, набрать заметку и оценку, добавить другую публикацию:
   несохранённый текст первой должен остаться. Сохранить её, изменить стадию и reload.
4. Включить мониторинг, сразу открыть настройки и сохранить: связь шаблона должна
   остаться. Проверить ту же публикацию во втором проекте с независимой стадией.
5. Повторить основные действия на телефоне; архивировать проект и убедиться, что
   просмотр остаётся доступен, изменения и собственный мониторинг приостановлены.
